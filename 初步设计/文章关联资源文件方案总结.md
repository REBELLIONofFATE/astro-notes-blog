# 文章关联资源文件方案总结

> 基于 2025-06-05 讨论整理，涵盖资源引用、附件展示、构建性能等问题与结论。

---

## 一、背景

阶段 1.5 实施计划中将"文章关联资源文件"列为末尾可选任务。本文档汇总围绕该任务展开的所有讨论、决策与待办事项。

---

## 二、讨论问题与结论

### 问题 1：Typora 能否管理资源文件？

**结论**：可以，通过隐式引用（文件放入同目录或 `filename.assets/` 子目录），但无独立的"附件管理器" UI。

### 问题 2：主流网站支持附件关联展示吗？

**结论**：普遍支持，方式各异：

| 平台 | 机制 |
|------|------|
| Hexo | Asset Folder（同名目录）+ `{% asset_link %}` 标签插件 |
| Fuwari | 仅 Markdown `![]()` 引用，无独立附件概念 |
| 语雀/Notion | 显式上传附件 + 底部面板/侧边栏展示 |

对本项目的启示：取 Hexo 的同目录隐式关联思路 + 语雀的纯静态构建方案，在文章正文中通过标准 Markdown 链接语法引用文件即可，不需做独立的"资源面板"或"文件查看系统"。

### 问题 3：一个目录多个 md + 多个资源文件，如何关联？

**结论**：同目录共享，不做所有权拆分。

```
spring/
├── spring-ioc.md          → 共享下方所有非 .md 文件
├── spring-aop.md          → 共享下方所有非 .md 文件
├── deploy-arch.png
├── spring-config.xml
└── spring-cheatsheet.pdf
```

目录结构天然表达了归属关系，按文件名拆分所有权会引入不必要的复杂度。

### 问题 4：附件引用与图片管理会冲突吗？

**结论**：技术层面零冲突。图片路径替换（`src`）和文件链接替换（`href`）是两个独立操作，数据源相同（同目录文件），输出目标不同。体验层面，正文引用的图片在底部再次列出不构成问题，主流平台（语雀、Notion）均全部列出。

### 问题 5：`[jquery-3.6.0.js](jquery-3.6.0.js)` 是 Typora 独有还是通用 Markdown？

**结论**：通用 Markdown 链接语法 `[text](url)`，所有 Markdown 实现均支持。问题不在语法，在文件是否在 Web URL 可访问路径下。

### 问题 6：当前系统是否兼容 `[file](file)` 写法？

**结论**：不兼容。当前 `asset-copier.ts` 的 `syncAndReplaceAssets` 只处理 `<img src="...">` 的路径替换，不处理 `<a href="...">`。

处理链路：
```
Markdown: [file](file.js)
  → marked 解析
  → <a href="file.js">
  → asset-copier：src 替换 ✅ / href 替换 ❌
```

**需补齐 `href` 替换逻辑**。

### 问题 7：分类菜单中是否应该展示附件？

**结论**：不应该。分类树是内容导航工具，只列 Markdown 文章/笔记。附件脱离文章上下文没有独立浏览价值。此结论与设计文档《博客与文件管理结合方案探讨》第五节一致。

### 问题 8：是否需要独立的文件查看系统？

**结论**：不需要。对个人博客而言，这是一个伪需求：
- 作者使用本地文件系统 + 编辑器已足够
- 读者来博客是看文章，不是翻文件夹
- 文件脱离文章上下文没有独立价值

设计文档《博客与文件管理结合方案探讨》第五节已有定论："对内知识库是伪需求"。

### 问题 9：跨目录资源引用能否兼容？

**结论**：当前不兼容跨 category 引用（如 `../../other/file.js`），原因有二：
1. `collectAssets` 扫描范围限定在 `mdDir`（md 所在目录），不向上遍历
2. 路径替换不处理 `href` 属性

**实际验证**：所有 vault 目录均含 `.md` 文件，不存在"纯文件目录无笔记"的情况，因此文件已全部被复制到 `public/`。唯一缺口是 `href` 跨目录替换逻辑。

**结论**：需同时解决两个层面——(1) 资源扫描独立化，确保无 .md 目录的资源不丢失；(2) 路径替换支持 `href` 属性 + 跨目录相对路径解析。

### 问题 10：构建体积是否有隐患？

**结论**：无隐患。当前 vault 非 md 文件总量 7.5M，对静态站点可忽略。文件扫描和复制不是构建瓶颈。

**真正的构建瓶颈**：`git log` 调用。

```
瓶颈排名：
1. git log（264 次串行 shell 调用）→ ~26s
2. Shiki 代码高亮                      → ~3s  
3. 同目录重复扫描                      → ~2s
```

### 问题 11：能否优化 git log 的性能？

**方案对比**：

| 方案 | git 调用 | 耗时 | `--follow` | 代码复杂度 |
|------|:---:|:---:|:---:|:---:|
| 当前（逐文件 execSync） | 264 次 | ~26s | ✅ | 中 |
| 单 shell 内循环 | 265 次 | ~8s | ✅ | 中 |
| **纯批量（推荐）** | **1 次** | **~1s** | ❌ | **低** |

**纯批量命令**：
```bash
git log --reverse --diff-filter=A --format="%aI" --name-only
```

一次命令输出所有文件的创建时间，解析后构建 `Map<filePath, Date>`，每篇笔记 O(1) 查表。

**`--follow` 丢失的容错分析**：
- 纯批量模式不支持 `--follow`（git 限制：多文件模式下 `--follow` 失效）
- 重命名过的文件日期取重命名当天的提交时间，非原始创建时间
- 实际影响：264 篇笔记中重命名文件 ≤ 3 篇，偏差可接受
- 即使有偏差，重命名日期也是一个真实存在的时间点，排序影响极小

**结论**：用 1% 的日期精度损失换 96% 的性能提升（26s → 1s）+ 更简洁的代码，完全值得。采用纯批量方案。

### 问题 12：资源扫描是否应该独立于 md 文件？

**现状**：资源文件的复制是每篇笔记处理的"副作用"——`syncAndReplaceAssets` 被各篇笔记调用时，顺便扫描和复制自身所在目录的资源。

**结构性缺陷**：如果某目录没有 .md 文件，该目录下的资源永远不会被复制到 `public/`。

```
vault/
├── spring/
│   └── spring-ioc.md        ← collectMdFiles 走到这里
│   └── spring-config.xml     ← 被 spring-ioc.md 触发复制 ✅
├── tools/
│   ├── useful-script.sh      ← 这个目录没有 .md 文件！
│   └── cheatsheet.pdf        ← 永远不会被扫描和复制 ❌
```

虽然当前 vault 所有目录均含 .md 文件，但这是一个结构性风险——未来新增纯资源目录将静默丢失。

**结论**：资源扫描必须独立于 md 文件处理，改为构建初期一次性全局遍历 vault 所有目录。

## 三、待办事项

### 任务 1：补全 `href` 路径替换

**文件**：`astro-blog/src/loaders/asset-copier.ts`

**改动**：在 `syncAndReplaceAssets` 函数中，紧邻现有 `src=` 替换逻辑，增加对 `href=` 的四类匹配替换：

- `href="relPath"` → `href="/notes-assets/{category}/{relPath}"`
- `href="./relPath"` → `href="/notes-assets/{category}/{relPath}"`
- `href="encoded"`（中文编码情况）
- `href="./encoded"`（中文编码情况）

同时支持跨目录相对路径（`../` 等）的正确解析。

### 任务 2：git log 改为纯批量模式

**文件**：`astro-blog/src/loaders/notes-loader.ts`

**改动**：将 `getFileDate` 函数从逐文件 `execSync` 改为批量模式：

```typescript
// 在 loader 初始化时执行一次，构建日期映射表
function buildDateMap(basePath: string): Map<string, Date> {
  const output = execSync(
    'git log --reverse --diff-filter=A --format="%aI" --name-only',
    { cwd: basePath, timeout: 10000 }
  ).toString();

  const map = new Map<string, Date>();
  let currentDate: Date | null = null;

  for (const line of output.trim().split('\n')) {
    if (!line) continue;
    const d = new Date(line);
    if (!isNaN(d.getTime())) {
      currentDate = d;
    } else if (currentDate) {
      const cleanPath = line.replace(/\\/g, '/');
      if (!map.has(cleanPath)) {
        map.set(cleanPath, currentDate);
      }
    }
  }
  return map;
}
```

构建耗时从 ~26s 降至 ~1s。

### 任务 3：资源扫描独立化（从 md 处理中解耦）
**文件**：`astro-blog/src/loaders/asset-copier.ts` + `astro-blog/src/loaders/notes-loader.ts`

**问题**：当前资源复制是笔记处理的"副作用"，无 .md 文件的目录资源会静默丢失。

**改动**：

1. 在 `asset-copier.ts` 中新增 `scanAllAssets(vaultRoot, buildIgnore)` 函数，遍历所有目录收集全部非 .md 文件，返回 `Map<category, Asset[]>`
2. 在 `notes-loader.ts` 的 load 函数中，先调用 `scanAllAssets` 全量复制资源，再逐篇处理笔记做路径替换
3. `syncAndReplaceAssets` 简化为只做路径替换（不再负责扫描和复制）

```typescript
// notes-loader.ts 流程变更

// === 阶段 1：全局资源扫描 ===
const allAssets = scanAllAssets(basePath, buildIgnore);
copyAllAssets(allAssets, notesAssetsDir);

// === 阶段 2：笔记处理 ===
for (const filePath of mdFiles) {
  let html = await md.parse(body);
  html = replaceAssetPaths(html, category, allAssets);  // 只替换，不复制
  store.set(...);
}
```

附带收益：消除同目录重复扫描，逻辑更清晰（数据准备与内容处理分离）。

## 四、不做的事情

| 事项 | 原因 |
|------|------|
| 文章底部"📎 相关资源"面板 | 作者想给读者看的文件，正文引用即可；无引用 = 不公开，自动展示有隐私风险 |
| 独立文件查看系统 | 伪需求，本地文件系统已是最佳管理工具 |
| 分类树中展示附件 | 分类树是内容导航，不是文件浏览器 |
