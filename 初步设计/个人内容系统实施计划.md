# 个人内容系统实施计划（阶段化）

> 目标：在保证**随时可停、可用、可重构**的前提下，逐步完成一个 Git-first 的个人内容系统。

---

## 总体原则（必须遵守）

- **内容优先于系统**：任何阶段都不允许“为了系统而阻塞写内容”。
- **事实源单一**：Git + Markdown 是唯一事实源，DB 永远可重建。
- **阶段可终止**：每一阶段结束后，系统都应处于“可长期使用”的状态。
- **只解决当前阶段问题**：不为未来需求提前设计。

---

## 阶段 0：准备与约束确认（1 周）

### 目标
- 防止系统膨胀
- 明确“不做什么”

### 具体任务
- 写一份《Design Goals & Non-Goals》
- 明确内容最小 Frontmatter schema（title / date / tags / status）
- 明确内容目录结构约定
- 明确构建触发方式（手动 / 脚本）

### 产出
- 设计文档（Markdown）
- 固定的 Frontmatter 约定

---

## 阶段 1：内容最小闭环（2–3 周）

### 目标
- **只解决一个问题：内容能被稳定发布**

### 范围
- 无数据库
- 无后端
- 无复杂前端

### 具体任务
- Git 仓库初始化（内容仓库）
- Markdown + Frontmatter 编写规范
- Astro 构建 Markdown 为文章页面
- 标签 / 分类基于构建期解析
- 手动构建 + 部署

### 验收标准
- 新增一篇 md → 构建 → 页面可访问
- 删除一篇 md → 页面消失

### 风险控制
- 不引入前端框架（Vue 等）
- 不引入数据库

---

## 阶段 2：内容索引与数据库派生层（3–4 周）

### 目标
- 引入 DB，但**不破坏 Git 事实源**

### 具体任务
- 设计内容索引表（article / tag / relation）
- 编写 md 解析器（Frontmatter → 结构化数据）
- 实现 Git → DB 的全量同步脚本
- 支持 DB 清空后重建

### 验收标准
- 任意时刻可删除 DB 并通过 Git 重建
- DB 中无业务逻辑，仅存索引与状态

### 风险点
- schema 演进不可逆
- 删除 / 重命名处理

---

## 阶段 3：构建与运行分离（2–3 周）

### 目标
- 明确区分“构建期系统”和“运行期系统”

### 具体任务
- Astro 专注构建静态页面
- Spring Boot 提供只读 API（文章 / 标签）
- API 数据完全来源于 DB 派生层
- 页面与 API 数据一致性校验

### 验收标准
- 页面与 API 返回文章列表一致
- 构建失败不影响运行期 API

---

## 阶段 4：前端交互增强（2 周）

### 目标
- 提升体验，但不引入系统复杂度

### 具体任务
- 使用原生 JS 实现客户端动态交互（评论、搜索、阅读量等）
- 页面静态优先，JS 增强
- 不做 SPA，不做状态管理
- 不引入前端框架

### 验收标准
- 无 JS 页面可完整阅读
- 动态功能（评论、搜索）通过原生 JS + API 调用实现
- 无任何前端框架依赖

### 可选（仅在原生 JS 难以维护时）
- 引入 Vue Islands 处理个别复杂交互组件（如嵌套评论）
- 通过 `npx astro add vue` 按需引入，不全局使用

---

## 阶段 5：自动化与稳定性（长期、低优先级）

### 目标
- 降低维护成本

### 具体任务
- Git pull → diff → 构建脚本
- 构建失败回滚策略
- 内容校验（Frontmatter 校验）

### 可选
- CI（GitHub Actions）
- 构建日志

---

## 阶段与风险对应表

| 阶段 | 最大风险 | 风险应对 |
|----|----|----|
| 0 | 目标膨胀 | 写 Non-Goals |
| 1 | 过早工程化 | 不用 DB |
| 2 | 数据不一致 | 可重建设计 |
| 3 | 系统耦合 | 严格分层 |
| 4 | 前端失控 | 原生 JS 优先，禁止 SPA |

---

## 推荐节奏（个人开发）

- 每周 3–5 次短时开发
- 每阶段结束至少写 1 篇内容
- 系统永远为内容服务

---

> **结束语**：
> 这个计划的目标不是“做完一个系统”，而是“在任何时间点，你都拥有一个你愿意长期使用的系统”。
